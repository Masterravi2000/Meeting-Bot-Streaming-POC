Cloudinary is fine for this — no real issue for a POC. A 5-minute 640×360 .mp4 is roughly 10-20 MB, well within the free plan's limits, and each file just becomes a direct URL your page can play. You can upload automatically from bot.js right after STITCH_COMPLETE with the Cloudinary Node SDK.

The real thing to handle is sync, not storage:

Different start times. Each .mp4 starts when that person's recording started (their join time), not when the meeting started. If Pintu joined 40s after you, pressing play on both at once puts him 40s early. Fix: have the bot save each participant's recording start timestamp (e.g. in a small JSON uploaded next to the videos), and the player delays or offsets each tile by that amount.
One master controller. Play, pause, and seek act on all videos together, and every second or so the page nudges any video that drifted more than ~0.2s back in line. Without this, tiles slowly drift apart.
People who left early. Their video ends before the others — show a black tile with their name for the rest, like Meet does.
Leftover files. The stale device-311 file from today would appear as a 4th tile. Either fix the session-ID naming first, or upload only the files from the current session.
The page itself is simple: a black stage, a responsive grid with one tile per .mp4 (2 → side by side, 4 → 2×2, and so on), each tile with the name label, and one control bar at the bottom driving everything.

Yes, that design is right and complete for the demo. To make it actually work, four things are needed:

A manifest from the bot. The page needs to know when each tile appears and disappears. So after stitching, bot.js should write a small JSON: for each participant — name, .mp4 URL, start offset (when their recording began relative to the meeting start) and duration. The page runs one master clock: a tile animates in when the clock reaches its start offset, and animates out when its video ends. Right now the bot doesn't save those start times, so that's a small addition in bot.js.
Auto-open after ffmpeg. After STITCH_ALL_DONE, bot.js uploads the files (Cloudinary), writes the manifest, then opens the page in your default browser — on Windows that's one line (start "" "path-or-url").
One catch — autoplay with sound. Browsers block videos from auto-playing with audio unless the user clicks first. So the page can open automatically, but it should either start muted, or show a big "Play meeting" button — one click and everything starts with sound. For a live demo, the button actually looks cleaner.
The page: white background, centered black stage, tiles that re-flow with a smooth animation as people join/leave, name label on each tile, and a bottom control bar (play/pause, seek bar, time) driving all videos together with drift correction.

No real load — and it can be arranged so the bot isn't touched at all during the meeting or the braking:

Start times: Node already sees each participant's first segment connect (WS_STREAM_OPEN ...::seg1). Saving Date.now() into a small object at that moment is one line in the existing wss.on("connection") handler — no browser work, no extra messages, nothing during correlation.
